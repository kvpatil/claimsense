# Synthetic data shapes

The shapes the pilot is built and demonstrated against. **Synthetic only** — no
production or personally identifiable data at any stage, which is the
constraint the CISO set and the architecture was designed around rather than
worked around.

Generated by `platform/db/seed/generate.py` from a **fixed seed (7731)**, so
every `make up` produces the same claims. That matters for more than tidiness:
an evaluation case that names claim 4405 has to mean the same thing on every
machine and in CI.

One generator emits **both** the Postgres seed and the agent's offline fixture
in a single pass. The agent must run with no database — `make verify` is the
$0 gate — so an offline copy has to exist, and generating it as a second
artifact of the same pass is what stops the two drifting. There is no
hand-maintained fixture to forget to update.

## Shapes

### Claim — CMS

| Field | Type | Example |
|---|---|---|
| `claim_id` | bigint | 4414 |
| `claim_number` | text | CLM-2026-4414 |
| `policy_id` | bigint | 7013 |
| `insured_id` | bigint | 9014 |
| `peril` | text | water |
| `date_of_loss` | text | 2026-09-18 |
| `reported_at` | text | 2026-09-19T13:00:00+00:00 |
| `claimed_amount_cents` | bigint | 2375000 |
| `status` | text | intake |
| `assigned_adjuster_id` | bigint | 2 |
| `loss_state` | text | CO |
| `acv_cents` | bigint | 41659200 |

`policy_id` and `insured_id` are **plain columns, not foreign keys.** PAS is
another vendor's database and there is no referential integrity across the
boundary — claim `4412` deliberately carries a `policy_id` PAS has never heard
of, so the pipeline has to survive a dangling reference rather than assume one
away.

`claimed_amount_cents` is **BIGINT cents**. There is no NUMERIC and no float
anywhere in the schema: a settlement is the number a claimant receives, and
floats make it a cent out occasionally and unpredictably.

### Policy — PAS

| Field | Type | Example |
|---|---|---|
| `policy_id` | bigint | 7013 |
| `policy_number` | text | HO3-007013 |
| `insured_id` | bigint | 9014 |
| `product` | text | HO3 |
| `effective_date` | text | 2026-01-23 |
| `expiration_date` | text | 2027-01-23 |
| `status` | text | active |
| `lapse_date` | nullable | None |
| `premium_cents` | bigint | 339800 |
| `payment_status` | text | current |

`lapse_date` non-null means cover ceased **before the term ended**. A loss on
or after that date has no cover even though it falls inside the policy period
— the distinction a naive term check misses, and the reason claim `4403`
exists.

### Policy clause — PAS

| Field | Type | Example |
|---|---|---|
| `clause_id` | text | HO3-I-EXCL-3b |
| `product` | text | HO3 |
| `section` | text | Section I — Exclusions |
| `title` | text | Water Damage — Sudden and Accidental Exception |
| `clause_type` | text | grant |
| `perils` | list | ['water'] |
| `body` | text | The water damage exclusion does not apply to sudden... |
| `keywords` | text | burst pipe pipes plumbing supply line hose washing ... |

`clause_id` is a **human-meaningful string**, not a serial. `HO3-I-EXCL-3b` is
what a coverage conclusion cites, what the console links to, and what an
adjuster looks up in the paper policy. An opaque integer would make a wrong
citation impossible to spot by eye.

`keywords` carries the vocabulary **claimants** use. A policy form is legal
register and a first notice of loss is written by someone whose house just
flooded; they share almost no words, and lexical retrieval scores on words.
Measured: without this field the wear-and-tear exclusion ranked *last of 25*
on a claim saying the roof "has been leaking".

### Document — DMS

| Field | Type | Example |
|---|---|---|
| `document_id` | bigint | 16 |
| `claim_id` | bigint | 4409 |
| `doc_type` | text | estimate |
| `filename` | text | 4409_estimate.pdf |
| `uploaded_at` | text | 2026-09-12T08:00:00+00:00 |
| `page_count` | bigint | 2 |
| `is_poisoned` | boolean | True |
| `extracted_text` | text | *(what OCR pulled out — the model reads this, never a file handle)* |

`is_poisoned` marks a document carrying text aimed at an automated reader. It
is **flagged, not filtered**: the API returns it and the input guardrail drops
it, because a quarantine that happens invisibly is a quarantine nobody can
audit.

### Fraud signal — CMS

| Field | Type | Example |
|---|---|---|
| `signal_id` | bigint | 1 |
| `claim_id` | bigint | 4405 |
| `indicator_code` | text | RECENT_INCEPTION |
| `detail` | text | Policy incepted 21 days before the date of loss. |
| `weight` | bigint | 25 |

`weight` ships **with** the signal so the score is reproducible by whoever
reads it. Summing weights is deterministic arithmetic; only what the total
*means* is judgment.

## The problems are in the data

Not described in a prompt — planted, so they are exercised rather than
asserted.

| Claim | Planted condition | Exercises |
|---|---|---|
| `4403` | policy lapsed for non-payment before the loss, inside the term | lapse beats term |
| `4407` | the claimant says "leaking"; the form says "deterioration" | retrieval vocabulary gap |
| `4409` | injection inside an estimate PDF — the only estimate on file | quarantine, and its cost |
| `4410` | date of loss one day before inception | date arithmetic over narrative |
| `4411` | claimed amount exactly equals the coverage limit | the off-by-one-cent boundary |
| `4412` | policy_id that PAS does not resolve | dangling cross-system reference |
| `4414` | burst supply line — same peril code as the flood case 4402 | exception vs exclusion |
| `4420` | injection in the claimant's own first notice of loss | cannot quarantine evidence |

## Privacy

| | |
|---|---|
| Names | drawn from a fixed list; no correspondence to real people |
| Email | reserved `.invalid` and `.example` domains — **can never route** |
| Addresses | state codes only; no street-level data exists |
| Policy numbers | generated from the row id |
| Clause text | synthetic wording modelled on the *shape* of an ISO-style form — **not any insurer's actual policy, and must not be used as one** |

A PII tripwire scans every drafted output and blocks on an SSN or card-number
pattern, or an email outside the reserved domains. It should never fire. If it
does, something upstream changed and the run stops and says so.

## Regenerating

```bash
make seed     # regenerate seed.sql + agent/data/fixture.json + the corpus copy
```

`tests/test_corpus.py` fails the build if the agent's corpus copy drifts from
the source, and `tests/test_backend_parity.py` runs all twenty planted claims
through both the fixture and the live API and compares outcome, citations and
verdict source field by field.
